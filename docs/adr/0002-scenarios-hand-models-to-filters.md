# Scenarios hand their raw models to filters

Status: accepted

A filter is constructed with a model object and the scenario's initial belief, and takes its noise values from the model rather than hard-coding its own. The model object holds the scenario's noise-free motion and measurement functions, its noise parameters (α-parameters, measurement standard deviations) and its landmarks.

The model deliberately hands over only raw ingredients: no Jacobians, noise covariance matrices, samplers, likelihoods or ready-made linear matrices. Deriving those is the predict and update work the user wants to do by hand.

The simulator generates ground truth and measurements with its own noise code, but reads the same functions and parameter values. That gives one source of truth: one filter class runs on every scenario, and scores cannot be silently invalidated by a filter using noise values that differ from the simulator's.

The only deliberate exceptions are scenarios that test robustness to the unmodelled: measurement outliers and kidnapping are generated by the simulator but absent from the model. The cost is that filters must be written against the model interface instead of literal matrices, and that the user must derive the filter maths themselves.
